# 调参面清单：改哪儿能改变出图

跑批回归之前先看这份。它的用处是——**回归数字动了，能照着这张表判断该调哪儿**；
反过来，**动了表上的任何一处，都该重跑回归**。

## 判定标准

不争论"什么算变量"，用操作性定义：

> **改动它，回归就该重跑的东西 = 变量。**

按这个标准，变量不止四份 SKILL + SOP 卡库，还包括 agent 读到的说明书、
它看到的报错文案、以及决定什么被剔除的判据。这些全都是喂给模型的中文或规则，
跟 skill 没有本质区别。

分四层，按"离出图多近"排序。

## 一条链路，题目是增强

产品是 **agent 驱动的 GeoGebra 画图工作台**——一条链路：把用户意图变成 GeoGebra 构造。
题目图片只是输入形态，**带了题图**时多拿一套建模知识（`get_expert_prompt`），不是换链路。
**要调的东西随「取了哪些知识包」而不同**：

| 场景 | 取什么 | 用到哪些变量 |
|---|---|---|
| 一般画图/改图 | `get_drawing_pack` | `generation-rules` + `ggb-basics` + **全库 18 张卡** + 工具描述 |
| 带了题目图片 | 上面 + `get_expert_prompt` | 再加 **4 份 SKILL 的 8 步建模方法论** + 本类清单（**纯文字题面不算**——只有题图才取） |

**画法统一**（2026-10-17）：立体图形的线框一律「建系 → 具名顶点 → 逐条 Segment 连真实棱」，
一步到位的 `Cube` / `Prism` / `Pyramid` **连自由画图也不用**。理由是**多轮微调是常态**：
第一轮图省事的 `Cube(A,B)`，到第二轮「在这条棱上加个动点」就给不出可引用的棱对象，
只能推倒重来。规则写在共同输出约定（`skills/shared/generation-rules.md`），所有场景都拿到，
具体写法指向 `3d-frame` / `3d-edges` 两张卡。

**回默认的样式行不写**（2026-10-17，实测）：线/线段/圆/圆锥曲线默认就是**黑色实线、线宽 5**——
`getColor` 为 `#000000`、线型 0，加不加 `SetColor(..., "Black")` / `SetLineStyle(..., 0)` 的
style XML 逐字节相同，写它们纯属空转（点与函数另有自己的默认色，要改色才写；线宽默认 5 够用，
不必调）。于是 `3d-edges` / `circle-tangent` / `curve-definition` 三张卡里这类行全部去掉：
同一道正方体的指令数从 51 行降到约 24 行。

**3D 取景写法定在 `ggb-basics`**（2026-10-17）：`CenterView` 定中心、`SetViewDirection` 定朝向、
`ZoomIn(倍率)` 是相对倍数（>1 放大，**负值会把缩放写成负数、画面报废**；默认视域约 ±9 单位，
棱长 1 的图形要 5~10 倍）。此前没有任何取景指引，实测 agent 只能猜——猜错两次（ZoomIn 方向反了）
才摸到正解，图还是偏小。图形太小是缩放的事，别拿朝向去救。

**打开课件时相机回标准**（2026-10-17）：3D 相机跨课件残留，而稿子里的取景只有相对缩放——
不回标准的话，同一份稿子在别的画布上会落到不同远近（实测叠到过立方体**内部**，视域只剩
±0.08 单位，看着像图没了）。现在进 3D 的**全量**路径（`useGgbSession`）顺手把相机也回标准，
于是稿子里的 `ZoomIn(k)` 可复现（守卫实测：8 → 恰好 ×8）。同一课件后续轮次走增量应用、
不会再回标准，用户手转的视角不会被抢；绝对手段都不在指令面上（实测：`SetViewDirection()`
不动缩放、2D 框缩放重载 `ZoomIn(x1,y1,x2,y2)` 在 3D 无效、`setCoordSystem` 是 JS API
不许进指令流），确定性只能由宿主给。

**派生点不许 `SetFixed`**（2026-10-17，实测）：`SetFixed(B, true)` 会把 `B = A + vx`
换成当前坐标常量、切断与上游的依赖——之后改 A 或 vx，B 都不跟着动。一条"顺手锁住全部顶点"
就能把整份稿子的可编辑性打掉（那正是"统一画法"要换来的东西）。规则已写进共同输出约定：
**只锁独立定点**。`3d-frame` 卡另补一句：`vx/vy/vz` 是纯计算对象，按 view 3 隐藏。

**换模式 = 视图也得换，与增量无关**（2026-10-18，实测+守卫）：daemon 的增量判定是
「新账本是不是当前账本的纯追加」，而**空画布 + 任何新账本**都算纯追加（`pureAppendDelta([], list)`
非空）。于是「新建课件 / `ggb_reset` 之后的第一份 3D 稿」被判成**增量** → 页面那段 3D 视图设置
（`setPerspective('T')` / 轴 / 网格 / 相机）整段被跳过 → 透视没切 → 3D 对象只在三维视图里画
（style XML 里 `ev="4"`）→ **用户看到整块白屏，而 `ggb_get_state` 里对象都在**。三个现场
（新建课件、清屏后、2D 课件改画立体）都是这条路；agent 往稿子里补 `SetActiveView(3)` 自救的也是它。
现在 `useGgbSession` 按**画布当前显示的模式**（透视 XML 的 512 位）决定要不要跑视图设置，
增量只决定要不要清屏。守卫：`node scripts/verify-3d-mode-switch.mjs`。

**标准视角的 zZero 取 -0.5**（2026-10-18，实测 + 观感裁定）：那块灰色「底板」（plate）
贴 z=0 画，**水平永远居中、竖直位置由相机中心的 z 决定**——998×648 画布、scale=50 时：
z=0 板正好落在画布中心（324 vs 324）、z=-1.5（GeoGebra 出厂值）低 70px（11%）。
观感上要"中间偏下一点"（图形坐在地上、z 轴朝上，留头顶空间），出厂的 11% 又太偏 ⇒ 取 −0.5
≈ 23px（3.5%）。板的位置没有 API/命令可调（`getGraphicsOptions(-1)` 里没有 plate 字段、
命令表里没有 ShowPlate/SetPlate），能动的只有相机。

⚠ **这个偏移是「世界单位 × 当前缩放」，不是画布比例**：agent 把视图放大 3 倍后，同一 −0.5
变成偏下 70px（11%）。要"任何缩放下观感一致"，得在稿子落地后按屏幕比例算
（`zZero = -比例 × 画布高px / scale`）——尚未做。

守卫里断言了这条（带板/不带板两张 PNG 相减取重心，要求落在中心下方 5~45px）。

判据侧随之：语义检查 2026-10-15 起**只剩动点自洽**（free_param / orphan_slider），
与类别无关，每次 `ggb_apply` 都跑。按类别的形状检查（`category_structure` / `no_text`）
已移除——它们与 SKILL 里的骨架要求重复，再 nag 一遍是同一件事说两遍。
所以调 SKILL 的 8 步**只影响取了增强的场景**，调 `ggb-basics` 或卡库**全都影响**。

这一层最容易被漏掉——它们不在 `skills/` 下，但同样是 prompt。

| 文件 | 控制什么 | 怎么调 | 谁守着 |

## 三、反馈侧：agent 看到的错

`packages/ggb-core/src/semantic.ts` 的 `detail` **不是报错文案，是给 agent 的指令**：

```
"存在文字对象 [...] 题目文字不应生成 Text 对象，请删除这些行"
"滑块 [...] 未驱动任何对象。若题目有动点，动点坐标应引用滑块"
"立体几何类题目：应为 3D 视图且含空间点…请按立体几何骨架重做"
```

| 文件 | 控制什么 | 怎么调 | 谁守着 |
|---|---|---|---|
| `semantic.ts` 的 `detail` 文案 | agent 拿到提示后怎么改 | 让提示更可执行、更少歧义 | `semantic.test.ts` 只要求**点出问题对象名**（含 `t`/`Slider`/`msg` 等），措辞可自由改，但不能把对象名从文案里去掉 |
| `ggb_apply` 的回传组织 | 明细怎么排序、合并、是否附图 | 调信息密度 | **无** |

改这一层出图质量会变，**别当成"日志"顺手改**。

## 四、判据侧：什么被剔除、什么算过

| 文件 | 控制什么 | 怎么调 | 谁守着 |
|---|---|---|---|
| `ggb_commands.json`（仓库根） | 命令白名单与签名；非法行**剔除不下发** | 加命令、修重载签名 | `test_command_catalog` + `verify_sops` |
| `semantic.ts` 的判定规则 | free_param / orphan_slider / category_structure 怎么判 | 调判据松紧 | `semantic.test.ts` |

`ggb_commands.json` 是**双端共享的单一事实来源**（TS `whitelist.ts` 与 Python
`ggb_parser.py` 同吃）。改它两边都会变，且 `verify_sops` 会拿它校验全部 55 个示例。

## 灰色地带（边界待定）

以下三条我倾向算变量，但可以争论，**跑批前建议先定下来**：

1. **MCP 工具面设计** —— 工具数量、schema、参数必填与否。
   例：`get_expert_prompt` 的 `category` 从可选改必填，agent 行为就变了
2. **A/B/C/D 四类划分本身** —— 边界题归哪类，直接决定取哪套 skill
3. **`agent-runtime` 的图片与转写处理** —— 图片没喂进去质量必崩，
   但更像基础设施故障而非参数

## 仓库外的变量

**agent CLI 自身的模型与系统提示**（claude-code / codex / dsh 各自的）。
绝对影响出图，但不在这仓库里。回归要覆盖它，得把 **CLI 与模型版本**也锁进 fixtures，
否则换台机器跑出来的数字不可比。

## 调参前必读

- **金基线已退役，改 skill/SOP 没有任何自动回归。** `verify_sops` 只抓结构
  （孤儿卡、嵌套引用、示例 id 与夹具一一对应、白名单、生产解析器），**不抓画得对不对**
- **动卡片要动夹具**：每块 ` ```ggb ` 前必须有 `<!-- example: id -->`，id 要与
  `scripts/sop_examples.json` 一一对应，否则 `verify_sops` 直接红
- **删卡要同步删槽位**：SKILL.md 里的 `{{SOP:card-name}}` 必须独占一行、无重复、
  位于编号步骤内；漏改会报「SOP 插入位置缺失或格式错误」
- **示例是实例不是常量**：数字、名字、范围按题意替换。别为套示例而添条件、缩范围
- 改完跑一遍：`python -B scripts/verify_sops.py` 与 `python -B scripts/test_command_catalog.py`

## 与 P3 的关系

P3 回归基准集就是给上面这些变量装仪表。建它之前先记住**旧判分为什么被删**：

- L1 金标准比对：构造偏见不可修复，已退役
- L2 性质判分：性质清单带 `point_at` 类构造习惯残留，13 例 L2=FAIL 而 L3=pass/partial
- L3 视觉判官：21 例里冤枉 2、放水 2

**共同病因是把"应该怎么构造"写进了判据。** 新判据要写成与构造方式无关的数学性质
（"抛物线过这两点、动点可拖且在轨迹上"），判官模型自身要有校准依据。
